The CLI surface is identical for `@geoql/vue-doctor` and
`@geoql/nuxt-doctor` — the latter just adds Nuxt-specific context
to the same engine. This page uses `@geoql/vue-doctor` for all
examples; swap the package name as needed.

## Synopsis

```bash
npx -y @geoql/vue-doctor [dir] [flags]
npx -y @geoql/vue-doctor <file|dir>... [flags]
npx -y @geoql/vue-doctor <subcommand> [flags]
```

### Positional paths

A single directory argument is the **project root** (the default is the
current directory) — `vue-doctor apps/web` audits that project exactly as
before.

Pass one or more **files** (or several files and directories) to audit the
project rooted at the current directory but report findings only for those
paths. Directories expand to the source files under them. Every path must
live inside the current directory, and a missing path exits `2`.

```bash
# just the files you touched
npx -y @geoql/vue-doctor src/components/Card.vue src/pages/index.vue

# a file plus everything under a directory
npx -y @geoql/vue-doctor src/App.vue src/composables
```

Positional paths combine with `--diff` / `--staged` /
`--changed-files-from`: only paths in **both** scopes are reported.

### Monorepos: nested workspace projects

Every pnpm workspace package is its own project — its own
`package.json`, framework, and doctor config. Auditing an ancestor
directory (for example the repo root) therefore **does not descend into
nested workspace packages**; their files are excluded from that scan, and a
stderr note lists what was skipped. Audit a nested package with
`--project <name>` (comma-separated for several, aggregated into one
report), by running from its own directory, or by passing one of its files
as a positional path. A package selected with `--project` is never counted
a second time inside an ancestor scan.

## Audit flags

These flags control the audit pass. They are the most-used subset.

| flag                         | description                                                                       | default       |
| ---------------------------- | --------------------------------------------------------------------------------- | ------------- |
| `--root <path>`              | project root to scan                                                              | cwd           |
| `--include <glob>`           | extra include glob (repeatable)                                                   | —             |
| `--exclude <glob>`           | extra exclude glob (repeatable)                                                   | —             |
| `--rule <id>:<level>`        | override a single rule's severity (repeatable). level = `error\|warn\|info\|off`  | —             |
| `--preset <name>`            | `minimal` \| `recommended` \| `strict` \| `all`                                   | `recommended` |
| `--category <cat>`           | only score rules in this category (repeatable)                                    | all           |
| `--dimension <dim>`          | only score this dimension (repeatable); `--dimension performance` = perf-only     | all           |
| `--format <fmt>`             | `agent` \| `pretty` \| `json` \| `json-compact` \| `sarif` \| `html`              | `agent`       |
| `--output <path>`            | write the report to a file (extension can imply format)                           | stdout        |
| `--fix`                      | apply auto-fixes where the rule supports it                                       | off           |
| `--fix-exclude <glob>`       | never auto-fix files matching this glob (repeatable)                              | —             |
| `--no-lint`                  | skip the oxlint subprocess pass                                                   | off           |
| `--respect-inline-disables`  | honor `// vue-doctor-disable-next-line` comments                                  | off           |
| `--scope <mode>`             | `full` \| `files` \| `changed` \| `lines` — how much of a change set to report    | `full`        |
| `--base <ref>`               | base ref for a non-full scope                                                     | auto          |
| `--staged`                   | use staged (index) changes as the change set                                      | off           |
| `--include-untracked`        | fold non-ignored untracked files into the change set                              | off           |
| `--diff`                     | **deprecated** — alias of `--scope files --base HEAD` (untracked included)        | off           |
| `--changed-files-from <ref>` | **deprecated** — alias of `--scope files` diffed directly against `<ref>`         | off           |
| `--full`                     | override the scope flags and audit everything                                     | off           |
| `--baseline <report.json>`   | report and gate only findings that are new vs a saved `--json` report             | off           |
| `--score`                    | print the score in CI-friendly format even when format is `json`                  | off           |
| `--annotations`              | emit `::error file=…::` GitHub-style annotations                                  | auto (in CI)  |
| `--threshold <n>`            | override the score threshold (0–100)                                              | `0`           |
| `--fail-on <level>`          | `error` \| `warn` \| `none` — when to exit non-zero                               | `error`       |
| `--verbose` / `--quiet`      | adjust log level                                                                  | default       |
| `--ci` / `--no-ci`           | force-enable or disable CI-only behavior (annotations, color)                     | auto          |
| `--include-test-files`       | Score findings in test/story files too (reported but unscored by default)         |
| `--max-duration <seconds>`   | soft time budget; on exhaustion, skip remaining passes and return partial results | —             |
| `--warning-exit-code <code>` | exit with `<code>` (2–255) when the gate finds warnings but no errors             | —             |

::callout{type="warning"}
`--fail-on` and `--threshold` are different. `--fail-on` controls
the **exit code** based on severity; `--threshold` controls the exit
code based on the **score**. You can use either, both, or neither.
::

### Scoping by git changes

`--scope` decides how much of a change set is reported:

| scope        | reports                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| `full`       | everything (default)                                                                                          |
| `files`      | every finding in the changed source files                                                                     |
| `changed`    | only findings **introduced** by the change (base revision re-audited, count-matched)                          |
| `lines`      | only findings whose source span touches a changed line (renames/shifts follow git)                            |
| `contextual` | findings on changed lines **plus** findings whose owning code (element, function, component, file) was edited |

```bash
# PR gate: fail only on what this branch introduced
npx -y @geoql/vue-doctor --scope changed --base origin/main

# review mode: findings on the lines you touched
npx -y @geoql/vue-doctor --scope lines

# pre-commit: findings in staged files
npx -y @geoql/vue-doctor --staged
npx -y @geoql/vue-doctor --scope lines --staged
```

The change set is the working tree (committed + uncommitted edits) diffed
against the **merge-base** of `HEAD` and `--base`. Without `--base`, the base is
auto-detected: `GITHUB_BASE_REF` (the PR base) on CI, else `origin/HEAD`, else
`main` / `master` (preferring `origin/`). `--staged` uses the git index vs
`HEAD` instead. `--include-untracked` folds non-ignored untracked files in as
whole-file additions. An unresolvable base exits `2`; `--full` overrides every
scope flag.

`changed` audits the base-revision copy of each changed file with the same
rules and filters, then applies the same count-based `(file, rule)` matcher as
`--baseline` (renames followed): pre-existing findings that merely moved or
were reformatted are not reported. The JSON `baseline` summary is filled with
`file: "git:<base>"`. Combine `changed` with `--baseline` to compare against a
saved report instead of re-auditing the base.

`contextual` is for teams that want existing findings surfaced in the code
they are editing. Each rule declares the owner a finding belongs to:

| owner              | meaning                                                       | examples                                                     |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------------ |
| `template-element` | the innermost template element (child elements excluded)      | `v-for-has-key`, `no-v-html`, `no-missing-alt`, design rules |
| `function`         | the innermost enclosing function (nested functions excluded)  | `watch-without-cleanup`, `no-lifecycle-after-await`          |
| `component`        | the whole SFC, or a `defineComponent(...)` / `export default` | `no-mixed-options-and-composition-api`, `vue/max-props`      |
| `file`             | the whole file                                                | `dead-code/unused-file`, `useSeoMeta-on-public-page`         |
| `line` (default)   | plain changed-line matching                                   | every rule without a declared owner                          |

A finding is reported when its owner contains an added or rewritten line or a
deletion. An edit in a sibling element or an unrelated function does not
surface it. When the owner cannot be resolved (parse error, no enclosing
node), the finding falls back to line matching. Ownership ranges are internal:
they never appear in the JSON report, SARIF, or `--push` payloads.

For every scope other than `full`, the score is computed over **all**
findings in the changed files (the formula is unchanged); `changed`, `lines`,
and `contextual` narrow only the listed findings, the severity counts, and the
gate. The JSON report gains `scope: { mode, base }`, and `--fix` is skipped.

`scope` and `base` can also be set in `doctor.config.*` (flags win).

The pre-`--scope` selectors keep working unchanged: `--diff` (=`--scope files
--base HEAD`, untracked included), `--staged`, and `--changed-files-from <ref>`
(=`--scope files` diffed directly against `<ref>`, no merge-base). `--diff`,
`--staged`, and `--changed-files-from` remain mutually exclusive, and `--diff` /
`--changed-files-from` cannot be combined with `--scope` / `--base`.

The scope flags work inside linked `git worktree` checkouts, including from
a git hook: doctor clears the inherited `GIT_DIR` / `GIT_WORK_TREE` before
it asks git for changed files, so the worktree's own index is read rather
than the main repository's.

### Scoping by category or dimension

`--category` and `--dimension` narrow the audit to a subset of rules.
Both are repeatable and compose (the scope is the union). They are
orthogonal to `--preset`/`--rule`: the preset decides which rules are
_on_, then the category/dimension scope keeps only the on-rules whose
category falls in the requested set.

```bash
# perf-only run — the most common case
npx -y @geoql/vue-doctor --dimension performance

# just security + the two perf categories
npx -y @geoql/vue-doctor --category security --dimension performance

# a single category
npx -y @geoql/vue-doctor --category reactivity
```

The six dimensions and the categories they cover:

| dimension         | categories                                                                   |
| ----------------- | ---------------------------------------------------------------------------- |
| `performance`     | `performance`, `template-perf`                                               |
| `correctness`     | `reactivity`, `composition`, `template`, `sfc`, `vue-builtin`, `hydration`   |
| `security`        | `security`                                                                   |
| `maintainability` | `ai-slop`, `dead-code`, `build-quality`, `deps`, `structure`, `modules-deps` |
| `nuxt`            | `nitro`, `seo`, `cloudflare`, `server-routes`, `data-fetching`               |
| `design`          | `design`                                                                     |

An unknown `--category` or `--dimension` value exits `2`. Scoping
re-scores from the surviving findings, so the printed score reflects
only the in-scope rules.

### Time-budgeting with `--max-duration`

`--max-duration <seconds>` sets a soft deadline for the whole audit.
When the budget is exhausted, doctor stops starting new passes (in
cost order: dead-code → template → lint → sfc → project), keeps every
finding already collected, and returns a **partial** result instead of
being killed with nothing.

```bash
# in CI, cap a slow monorepo scan at 90s
npx -y @geoql/vue-doctor --max-duration 90 --format json
```

The score stays a real number (√-decay over the findings that _were_
collected) and the exit code still follows `--threshold` / `--fail-on`
— a time-out never changes those. In `json` output the report gains:

```jsonc
{
  "incomplete": true,
  "skippedCheckReasons": [
    {
      "kind": "time-budget-exhausted",
      "deadlineMs": 90000,
      "elapsedMs": 90420,
      "skippedPasses": ["dead-code", "project"],
    },
  ],
}
```

On a run that finishes within budget, `incomplete` is omitted (the
JSON is byte-for-byte what you get today) and `schemaVersion` stays
`"1"`.

### Baselines: gate only new findings

Save a full `--json` report once, then pass it back with `--baseline` to
report and gate only the findings that are **new** relative to it — the way to
adopt doctor on a codebase with existing debt without fixing everything first.

```bash
# on main: record today's findings
npx -y @geoql/vue-doctor --json --output doctor-baseline.json

# on a branch / in CI: fail only on what this change introduced
npx -y @geoql/vue-doctor --baseline doctor-baseline.json
```

How matching works:

- Every JSON diagnostic carries a `fingerprint`: a hash of the rule id, the
  project-relative path, and the whitespace-normalized source the finding
  points at. **Line numbers are not part of it**, so code that merely moved
  keeps its identity.
- Findings are grouped by `(file, rule)`. Git renames since the baseline's
  `sourceRevision` are followed — including a tracked file that was deleted
  and recreated as an untracked file under a new name.
- A group whose count did not grow reports **nothing** new (reformatting and
  moving code never surface as regressions). A group that grew reports exactly
  the increase; which findings are new is decided by fingerprint, then message,
  then git-adjusted line distance.

The gate (`--fail-on`), the severity counts, and the listed findings cover
new findings only. **The score is unchanged**: it is still computed over all
current findings with the same √-decay formula, so the number keeps tracking
the project's real health. `--push` likewise sends the full current findings.
The JSON report gains a summary:

```jsonc
{
  "baseline": {
    "file": "doctor-baseline.json",
    "matchedCount": 41,
    "newCount": 2,
    "fixedCount": 5,
  },
}
```

The baseline must be a complete, plain `--json` report from a version that
writes fingerprints, produced with the same finding-affecting settings — rules,
preset, `--category`/`--dimension`, include/exclude, inline-disable handling,
and enabled passes. Those settings are recorded as `configHash`; a missing or
different hash, an `incomplete` report, or a report that is itself a baseline
comparison exits `2` with an explanation. Regenerate the baseline after
changing any of them.

### Test and story files

Findings in test, story, and fixture files (`*.test.*`, `*.spec.*`,
`*.stories.*`, `__tests__/`, `tests/`, `cypress/`, `e2e/`, ...) are still
reported — each carries `"surface": "test"` in the JSON output — but they are
**excluded from the score and the CI gate** by default. Your test helpers
shouldn't drag down your production health score.

Route files that merely happen to be named `test` (`pages/test.vue`,
`server/api/tests.get.ts`) stay production surface.

Opt test findings back into the score with the flag or config:

```bash
npx @geoql/vue-doctor --include-test-files
```

```ts [doctor.config.ts]
export default defineConfig({
  includeTestFiles: true,
});
```

### Dead code in Vite projects with auto-import plugins

The dead-code pass (knip) cannot see files and packages that build-time
plugins resolve without an `import`. On plain Vue 3 + Vite projects, doctor
reads `vite.config.{ts,mts,js,mjs}` and registers what these plugins resolve,
so they are not reported as unused:

| Plugin                                                    | Read from vite.config                      | Default when omitted |
| --------------------------------------------------------- | ------------------------------------------ | -------------------- |
| `unplugin-auto-import/vite`                               | `dirs` (entry files), `imports` (packages) | none                 |
| `unplugin-vue-components/vite`                            | `dirs`                                     | `src/components`     |
| `unplugin-vue-router/vite`, `vue-router/vite`             | `routesFolder`                             | `src/pages`          |
| `vite-plugin-pages`                                       | `dirs`                                     | `src/pages`          |
| `vite-plugin-vue-layouts`, `vite-plugin-vue-layouts-next` | `layoutsDirs`                              | `src/layouts`        |

Only string literals are read. A package named in an AutoImport `imports`
preset (for example `pinia` or `@vueuse/core`) is not reported as an unused
dependency. Files outside these dirs that nothing imports are still reported.

## Subcommands

### `list-rules`

Print the registered rule catalogue. Use `--json` or `--json-compact`
to get a machine-readable form.

```bash
npx -y @geoql/vue-doctor list-rules
npx -y @geoql/vue-doctor list-rules --category hydration --json
```

Filters:

| flag               | description                                                                                                      |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `--preset <name>`  | restrict to rules enabled by the given preset                                                                    |
| `--category <cat>` | `ai-slop` \| `composition` \| `performance` \| `reactivity` \| `hydration` \| `data-fetching` \| `server-routes` |
| `--source <src>`   | `oxlint` \| `core`                                                                                               |
| `--severity <sev>` | `error` \| `warn` \| `info`                                                                                      |
| `--tag <tag>`      | only rules carrying this tag (see below)                                                                         |

Every rule carries one or more **tags** — behavioral families that cut
across categories. The table shows them as `#tag`, and `--json` /
`explain --json` include a `tags` array.

| tag              | rules                                                                  |
| ---------------- | ---------------------------------------------------------------------- |
| `vue` / `nuxt`   | the framework the rule belongs to                                      |
| `design`         | design-quality rules (Tailwind, color, decoration)                     |
| `ai-slop`        | AI-agent anti-patterns                                                 |
| `security-scan`  | security rules                                                         |
| `test-noise`     | rules that are mostly noise in tests and fixtures (dead exports, etc.) |
| `performance`    | performance and template-performance rules                             |
| `hydration`      | Nuxt hydration traps                                                   |
| `dead-code`      | knip dead-code findings                                                |
| `migration-hint` | deprecated APIs and outdated-major / Nuxt 4 migration checks           |

Tags drive config [`ignore.tags`](/config/reference#ignore) and the
per-surface `includeTags` / `excludeTags` [controls](/config/reference#surfaces).

### `rules`

With no action, `rules` is an alias of `list-rules` (same filters). With an
action it edits the project's doctor config for you:

```bash
npx -y @geoql/vue-doctor rules set vue-doctor/security/no-v-html warn
npx -y @geoql/vue-doctor rules disable vue-doctor/design/no-raw-hex-color
npx -y @geoql/vue-doctor rules enable vue-doctor/design/no-raw-hex-color
npx -y @geoql/vue-doctor rules explain vue-doctor/security/no-v-html
```

| action                                      | effect                                     |
| ------------------------------------------- | ------------------------------------------ |
| `set <rule> <off \| info \| warn \| error>` | write `rules['<rule>']` with that level    |
| `disable <rule>`                            | same as `set <rule> off`                   |
| `enable <rule>`                             | set the rule back to its registry severity |
| `explain <rule>`                            | same as [`explain`](#explain-ruleid)       |

The config is found the way `init` lays it out: an existing
`doctor.config.{ts,mts,js,mjs}` is edited in place (comments and the rest
of the file are kept), a `doctor.config.json{,c}` or `package.json#doctor`
is edited as data, and with no config a `doctor.config.json` is created.
`--dir <path>` picks the project (default `.`) and `--dry-run` prints the
result without writing. An unknown rule id or level exits `2`.

### `explain <ruleId>`

Print the long-form description, the rationale, and the recommended
fix for a single rule.

```bash
npx -y @geoql/vue-doctor explain no-em-dash-in-str
```

The output is the same text that appears in the docs at
`/rules/vue` and `/rules/nuxt`, but reachable from the terminal.

### `inspect [dir]`

Print the detected project profile: framework versions, capabilities
(auto-imports, Pinia, Vue Router), monorepo layout, and the rules
that would be enabled under the active preset.

```bash
npx -y @geoql/vue-doctor inspect
npx -y @geoql/vue-doctor inspect apps/web --json
```

Useful in CI to debug "why is rule X not firing on this project?".

The JSON report's `projectInfo` carries a `frameworkDetected` boolean
(`true` when a Vue or Nuxt project is detected, `false` otherwise) so a
consumer can tell a real audit apart from a scan that found no Vue/Nuxt
project — without string-matching `framework`.

### `init`

Generate a `doctor.config.ts` in the current directory. Interactive by
default; pass `--yes` to accept defaults.

```bash
npx -y @geoql/vue-doctor init --yes
npx -y @geoql/vue-doctor init --yes --config-format json
```

The init flow asks five questions (preset, output format, fail-on
threshold, file scope, ignore globs) and writes a typed config that
matches the [config schema](/config/reference).

### `install [dir]`

Scaffold the agent skill (`.agents/skills/vue-doctor/SKILL.md`, with a
`.claude -> .agents` link when `.claude` is absent) so coding agents run the
doctor after changes.

```bash
npx -y @geoql/vue-doctor install --yes

# also install end-of-turn hooks for Claude Code and Cursor
npx -y @geoql/vue-doctor install --yes --agent-hooks
```

| flag            | description                                         | default |
| --------------- | --------------------------------------------------- | ------- |
| `--agent-hooks` | also write Claude Code and Cursor end-of-turn hooks | off     |
| `-y`, `--yes`   | write without prompting                             | off     |
| `--force`       | overwrite an existing skill                         | off     |
| `--dry-run`     | print the planned files, write nothing              | off     |

`--agent-hooks` writes:

- `.claude/settings.json` — a `Stop` hook running
  `node "$CLAUDE_PROJECT_DIR/.claude/hooks/vue-doctor.mjs"`, plus that script;
- `.cursor/hooks.json` — a `stop` hook running
  `node .cursor/hooks/vue-doctor.mjs` (120 s timeout), plus that script.

At the end of each agent turn the script runs
`vue-doctor --diff --fail-on warn --no-dead-code` on the changed files (the
local `node_modules/.bin` CLI first, then a global one, then
`pnpm dlx` / `npx`). When it finds issues, Claude Code is told to keep
working (`decision: "block"`) and Cursor gets a follow-up message with the
findings; a clean run or a doctor error (exit `2`, e.g. outside a git checkout) is silent. It never re-fires on its own follow-up
turn.

The install is idempotent and merges with what is there: existing
settings keys, other events, and other hooks are kept, and only the
doctor's own entry is replaced. Re-running `install --agent-hooks` keeps an
existing skill. A settings file with invalid JSON exits `2` untouched.

### `ci install`

Scaffold a CI workflow that runs doctor on every push and pull request.
It writes a workflow which uses the published
[`geoql/doctor-action@v2`](https://github.com/geoql/doctor-action) — it
does **not** inline an `npx` run, so upgrades come for free from the
action's floating major tag.

```bash
# GitHub Actions (auto-detected) — writes .github/workflows/doctor.yml
npx -y @geoql/vue-doctor ci install

# preview without writing
npx -y @geoql/vue-doctor ci install --dry-run

# also scaffold a PR-review workflow; skip inline PR comments
npx -y @geoql/vue-doctor ci install --pr --no-comments
```

| flag                | description                                                    | default  |
| ------------------- | -------------------------------------------------------------- | -------- |
| `--pr`              | also scaffold a separate PR-review workflow                    | off      |
| `--no-comments`     | strict gate only — omit the PR-comment inputs                  | comments |
| `--provider <name>` | `github` \| `gitlab` \| `auto` (GitLab writes a gate-only job) | `auto`   |
| `-y`, `--yes`       | write without prompting                                        | off      |
| `--force`           | overwrite an existing workflow                                 | off      |
| `--dry-run`         | print the planned files, write nothing                         | off      |

The scaffolded workflow wires `api-key` to `secrets.DOCTOR_API_KEY` and
sets `push-project`, so pushing scores to the
[dashboard](https://app.the-doctor.report) only needs you to add the
secret. `framework` is fixed to the CLI you ran (`vue` for
`vue-doctor`, `nuxt` for `nuxt-doctor`). `ci upgrade` and `ci config`
are intentionally not provided — the floating `@v2` tag handles
upgrades, and gate/scope/PR settings live on the audit flags and the
action's `with:` block.

Run from a nested package (or pass its directory) and the workflow is
written at the **git repository root** — `.github/workflows/` only works
there — with `working-directory: <package>` set on the action (GitLab: a
`cd <package> &&` prefix). Inside a linked `git worktree`, the root is that
worktree's top level.

### `design [dir]`

Runs a focused design-quality scan — accessibility, interaction states,
forms, and production polish — powered by
[shadscan-vue](https://github.com/vinayakkulkarni/shadscan-vue). The design
score is its own weighted 0-100 and never affects the health score.

```bash
npx @geoql/vue-doctor design .
npx @geoql/vue-doctor design . --format json
npx @geoql/vue-doctor design . --fail-under 70
```

| Flag                   | What it does                            |
| ---------------------- | --------------------------------------- |
| `--format <name>`      | `human` (default), `json`, or `agent`   |
| `--fail-under <score>` | Exit 1 when the design score is below N |

## Dashboard push (the-doctor.report)

When you run doctor in CI, it can stream **privacy-stripped** findings to
your [the-doctor.report](https://app.the-doctor.report) dashboard so the
score, severity counts, and per-rule findings show up over time.

| flag                      | description                                                                  | default                                         |
| ------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------- |
| `--push`                  | after the audit, POST findings to the SaaS (negate with `--no-push`)         | off                                             |
| `--api-key <key>`         | the-doctor.report API key (`doc_…`); pass via a secret, never inline         | —                                               |
| `--push-project <slug>`   | dashboard project slug (e.g. `owner/repo`); falls back to the directory name | audited dir name                                |
| `--push-workspace <path>` | sub-app label inside a monorepo project (e.g. `apps/docs`)                   | none (single-app repo)                          |
| `--push-url <url>`        | SaaS endpoint for the push                                                   | `https://app.the-doctor.report/api/v1/findings` |

```bash
npx -y @geoql/vue-doctor \
  --push \
  --api-key "$DOCTOR_API_KEY" \
  --push-project "owner/repo"
```

### Monorepos: one project, one score series per workspace

A repo that ships a Vue library _and_ a Nuxt app has two codebases with two
very different scores. Push them under the same `--push-project` slug and
tag each with `--push-workspace`, and the dashboard keeps a separate score
series, findings list, and leaderboard row per sub-app — instead of the two
runs overwriting each other on every commit.

```bash
# Vue library
npx -y @geoql/vue-doctor packages/my-lib \
  --push --api-key "$DOCTOR_API_KEY" \
  --push-project "owner/repo" --push-workspace "packages/my-lib"

# Nuxt docs app in the same repo
npx -y @geoql/nuxt-doctor apps/docs \
  --push --api-key "$DOCTOR_API_KEY" \
  --push-project "owner/repo" --push-workspace "apps/docs"
```

::callout{type="tip"}
With [`geoql/doctor-action@v2`](https://github.com/geoql/doctor-action) you
do not pass this flag at all — the action forwards its own
`working-directory` as the workspace. Run the action once per sub-app and
each gets its own series automatically.
::

::callout{type="warning"}
Omitting `--push-workspace` in a monorepo makes every sub-app share one
untagged series. Runs from the same commit then collapse to the newest
one, so one app's score silently replaces the other's.
::

::callout{type="warning"}
`--push-project` is **not** the same as `--project`. `--project` is the
monorepo workspace-aggregation filter (audit named workspace packages);
`--push-project` is the dashboard slug. Passing an `owner/repo` slug to
`--project` makes the CLI look for a workspace package by that name, find
none, and exit `2`.
::

::callout{type="tip"}
Only privacy-safe fields are sent: rule id, severity, category, file path,
and line/column. **Never** your source code, code snippets, or messages.
A failed push never changes the audit exit code — a down dashboard will
not break your CI.
::

## Output formats

| format         | best for                                  | shape                                |
| -------------- | ----------------------------------------- | ------------------------------------ |
| `agent`        | local dev, CI logs (default)              | one-line summary + per-finding block |
| `pretty`       | local dev, human reading                  | boxed tables with rule descriptions  |
| `json`         | programmatic consumption                  | full `AuditReport` JSON              |
| `json-compact` | high-volume CI                            | single-line JSON per finding         |
| `sarif`        | GitHub code scanning, GitLab code quality | SARIF 2.1.0                          |
| `html`         | shareable report (emailable, PR comment)  | self-contained HTML                  |

The format is auto-detected from the `--output` extension if you
don't pass `--format`. `.json` → `json`, `.sarif` → `sarif`,
`.html` → `html`, anything else → `agent`.

## Exit codes

Stable across all subcommands:

| code | meaning                                                              |
| ---- | -------------------------------------------------------------------- |
| `0`  | success — score above threshold, no findings at or above `--fail-on` |
| `1`  | at or above `--fail-on` threshold (or score below `--threshold`)     |
| `2`  | invalid arguments, missing config, doctor crash, or I/O error        |
| `N`  | warnings only, when `--warning-exit-code N` is set (2–255)           |

### `--warning-exit-code`

By default a run with warnings but no errors exits `0` (or `1` under
`--fail-on warn`). `--warning-exit-code <code>` makes that case exit with
`<code>` instead, so CI can mark the job as "passed with warnings" —
for example GitLab's `allow_failure: { exit_codes: [78] }`:

```yaml
doctor:
  script:
    - npx -y @geoql/vue-doctor --warning-exit-code 78
  allow_failure:
    exit_codes: [78]
```

Errors still exit `1`, a crashed pass still exits `2`, and the flag is
ignored with `--fail-on none` (advisory run) and with `--score`. Values
outside 2–255 exit `2`.

::callout{type="tip"}
If your CI script does `if [ $? -ne 0 ]; then fail; fi`, it will
correctly catch both code `1` and code `2`. If you want to treat
exit `2` as a separate failure (e.g., page on-call), check for it
explicitly: `if [ $? -eq 2 ]; then pager …; fi`.
::

## Environment variables

| variable          | equivalent flag | notes                             |
| ----------------- | --------------- | --------------------------------- |
| `DOCTOR_NO_COLOR` | `--no-color`    | disable ANSI in output            |
| `DOCTOR_PRESET`   | `--preset`      | picked up before the CLI flag     |
| `DOCTOR_FAIL_ON`  | `--fail-on`     |                                   |
| `DOCTOR_FORMAT`   | `--format`      |                                   |
| `DOCTOR_ROOT`     | `--root`        |                                   |
| `CI`              | —               | auto-enables annotations when set |
| `GITHUB_ACTIONS`  | —               | also auto-enables annotations     |

The CLI flag always wins over the env var. The env var is useful for
shell aliases and CI matrix defaults.
